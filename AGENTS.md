# Repository Guidelines

getona.horse is a booking system for horse-riding stables (account roles: `instructor` — Instruktor; `rider` — Jeździec. A stable's owner — Właściciel — is the instructor account with every right in it, ADR-0004) built on Astro 6 SSR + React 19 islands + Supabase (auth/Postgres) + shadcn/ui, deployed to Cloudflare Workers. UI copy is Polish.

## Where things are written down

- **Domain vocabulary and decisions** — `GLOSSARY.md`, `docs/adr/`. Use the glossary's terms in code, tests and copy.
- **Visual system and how it is implemented** — `DESIGN.md` (§8 covers tokens, shared blocks, charts, scoped-style traps). Read it before touching markup or styles.
- **Test patterns** — `context/foundation/test-plan.md` §6: unit (§6.1), database (§6.2), e2e incl. locator traps and reserved seed slots (§6.3), endpoints (§6.4), gates and the edit hook (§6.6).
- **Review rules** — `CODING_STANDARDS.md`. Read it when reviewing a diff.
- **Recurring pitfalls** — `context/foundation/lessons.md`.
- **Product** — `context/foundation/prd.md`, `roadmap.md` (living docs, edited in place). `context/changes/<id>/` holds in-flight change folders; `context/archive/` is immutable.
- **Commands** — `package.json` scripts; CI — `.github/workflows/ci.yml`.

## Hard rules

- `main` accepts only pull-request merges with `ci`, `db-tests` and `e2e` green (ruleset `.github/rulesets/main-gates.json`). Production deploys from `main` through Cloudflare Workers Builds, not Actions.
- `src/db/database.types.ts` is generated: after any schema change run `npm run db:types` (local stack running) and commit the result. The rest of the app imports the domain aliases in `src/types.ts`.
- Three test layers, each the only guard for its area:
  - `npm test` (Vitest) — pure logic under `src/lib/**` only.
  - `npm run test:db` — database guarantees. Run after ANY change to migrations or RLS. Needs a seed loaded today and untouched: `npx supabase db reset` first.
  - `npm run test:e2e` (Playwright) — the only layer that exercises SSR pages, forms, redirects and cookies. Run after any change to `src/pages/**`, RLS on `bookings`, or the seed.
- The seed schedules only tomorrow. Past history for the statistics page is `supabase/demo/history.sql`, loaded by `npm run db:demo` and by the e2e setup. Once loaded, `npm run test:db` needs a fresh `npx supabase db reset`.
- The built worker reads secrets from the `.dev.vars` snapshot taken at `astro build`, never from the process environment. `.dev.vars*` hold secrets.
- `npm run lint` is ESLint plus `scripts/check-tokens.mjs`, which rejects colour and font literals outside `src/styles/global.css`.
- A new migration is named `YYYYMMDDHHmmss_short_description.sql` and enables RLS on every table it creates.
- After `npx supabase link`, copy `supabase/.temp/postgres-version` over the committed `supabase/postgres-version` if they differ — CI pins its Postgres image from the committed file.
- This machine is short on memory. In a git worktree run `node scripts/agent-worktree.mjs setup <base-branch> <new-branch>` instead of `npm install`, and `node scripts/agent-worktree.mjs teardown` when done; start the dev server or Docker only when asked.

## Database

- A slot is one instructor × one hour of a schedule day with a seat limit (`schedule_slots.seats`, ADR-0002); `hour` is a `smallint`, working hours are the half-open range `[open_hour, close_hour)` — 10–16 means slots 10…15. A rider books a seat with an instructor (`bookings.instructor_id`); the horse (`bookings.horse_id`) is optional and only on an active booking — the stable assigns it.
- The seat limit is the trigger `bookings_seat_limit`, not application code: it locks the slot row (`FOR UPDATE`) and refuses a booking over the limit with `SB009`; a missing slot or day surfaces as `23503`, "outside working hours" as `23514`. One active booking per rider per hour is the partial unique index `bookings_rider_hour_key` (`23505`); one active booking per assigned horse per hour is `bookings_horse_hour_key`. Trigger `bookings_cancellation` makes a cancelled booking final, lets each role write only itself into `cancelled_by` (`42501`) and clears the horse. Only the owner or the instructor of the booking's slot changes `horse_id` (trigger `bookings_horse_assignment`, `42501` otherwise; no time threshold) — the owner by a plain UPDATE under RLS, an instructor only through `public.assign_my_slot_horse(booking, horse)`, which writes nothing but the horse (horses to pick from, with a „zajęty” flag and no rider data: `public.get_my_slot_horse_options(from)`); the "slot already started" threshold for cancelling — by either role — lives in the endpoints. Rider-facing messages live in `src/lib/bookings/errors.ts`; stable-facing schedule codes (`SB001`–`SB011`) in `src/lib/schedule/errors.ts`; horse-assignment refusals in `src/lib/bookings/stable-errors.ts`.
- The schedule (day, horses, instructors, seat limits) is written only by `public.save_schedule_day`, in one transaction; direct INSERT/UPDATE/DELETE on `schedule_days`, `schedule_day_horses`, `schedule_day_instructors` and `schedule_slots` is revoked (`42501`). Seeds and demo data write as `postgres` and must keep the seat-sum rule themselves.
- `bookings.rider_id` is nullable: NULL means an anonymised rider (ADR-0001). Deleting a profile first deletes all of the rider's bookings whose slot hour has not ended (trigger `profiles_release_future_bookings`, boundary `private.booking_slot_ended` in `Europe/Warsaw`), then the FK sets `rider_id` to NULL on the rest. Any code that shows a rider next to a booking handles the missing rider.
- Account role is `profiles.role` in (`instructor`, `rider`), immutable. An instructor account is linked to at most one instructor (`instructors.account_id`, unique, never writable by `authenticated` and not readable by `anon`/`authenticated` either — SELECT is granted on the other columns only, so `select=*` or a filter on `account_id` fails with `42501`). The account's own instructor comes from `public.my_instructor()` (`getOwnInstructor`), which instructors of the owner's stable have an account (and which is the owner) from `public.list_instructor_accounts()` (`listInstructorAccounts`). The stable context is `private.current_stable_id()` (stable of the account's ACTIVE instructor); everything a stable does — schedule, horses, instructors, bookings, horse assignment, cancellation, statistics — requires the owner, `private.owned_stable_id()` (`private.is_stable_owner()`, `private.current_instructor_id()` alongside); the one exception is the schedule, whose stable is `private.schedule_stable_id()` (owner's stable, or that of an ACTIVE instructor with the schedule permission; `public.schedule_stable_id()` / `getScheduleStableId` for the app) — `save_schedule_day` and the SELECT policies the schedule form needs (schedule days, day horses, day instructors, slots, the stable's horses and instructors) and `get_slot_occupancy` use it. A stable is created only by `public.create_stable(name, city, instructor_name)` together with its owner instructor (direct INSERT on `stables` is revoked); the owner cannot be deactivated (`SB012`). `cancelled_by = 'stable'` still means "cancelled by the stable", i.e. its owner. An instructor account that is not the owner reads only its own slots, their schedule days, its own instructor row and stable name, and ACTIVE bookings on its slots; rider names and the assigned horse come from `public.get_my_slot_bookings(from)` (RLS on `profiles` is not loosened), and for its month summary (`/instruktor/podsumowanie`, tab „Podsumowanie miesiąca” of every active instructor with an account) from `public.get_my_month_bookings(from, to)` with a rider key (the account; NULL plus `anonymised` for an anonymised rider); it assigns horses on its own slots in „Moje sloty” (`POST /api/bookings/instructor-assign-horse`). Riders and the owner keep the open catalogue read (`private.reads_catalogue()`). The schedule permission (GLOSSARY „Uprawnienie do układania grafiku”) is `instructors.arranges_schedule` — like `account_id` neither readable nor writable by `authenticated`; the owner reads it in `list_instructor_accounts()`, the account its own in `my_instructor()`, and only the owner changes it through `public.set_schedule_permission(instructor, granted)` (`42501` not an owner, `SB013` foreign instructor, `SB023` no account, `SB024` inactive, `SB025` the owner himself; messages `schedulePermissionErrorMessage`). CHECK `instructors_schedule_permission_standing_check` keeps it on active instructors with an account only; trigger `instructors_lost_standing_drops_schedule_permission` clears it on deactivation or account loss, reactivation does not restore it. Deactivating an instructor empties that context, so its account reads nothing — no separate logic; reactivation restores it without a new invitation. Routing: owner → `/osrodek`, instructor → `/instruktor` („Moje sloty”); an instructor with the schedule permission (standing `arranging-instructor`) also gets the „Grafik” tab `/instruktor/grafik` (`instructorTabs`, component `InstructorTabs.astro`; same `ScheduleDayPage.astro` and `POST /api/schedule/save` as the owner, return route `scheduleRouteFor`; refused `42501` → `/instruktor?error=` „Nie masz już uprawnienia do układania grafiku”, `scheduleErrorMessage(code, detail, caller)`), without it that path redirects to „Moje sloty”; deactivated instructor → `/instruktor/konto-nieaktywne` from every protected route (`my_instructor()` still returns its instructor with `active = false`), decided by `instructorStandingOf` / `instructorRedirect` in `src/lib/auth/roles.ts` (`locals.instructorStanding`).
- Instructor invitations (`instructor_invitations`) are closed to `authenticated`; the owner works through `public.issue_instructor_invitation` / `revoke_instructor_invitation` / `list_instructor_invitations` (refusals `42501`, `SB013` foreign instructor, `SB014` inactive, `SB015` already has an account, `23514` bad address). Only `sha256` of the token is stored; the token travels once, in the link `/auth/signup?zaproszenie=<64 hex>`. Deactivating an instructor revokes its open invitation in the same transaction (trigger `instructors_deactivation_revokes_invitation`), so reactivation never revives an old link. The sign-up page reads it anonymously through `public.invitation_by_token` (stable name, address, state). Acceptance happens inside account creation: sign-up metadata `invitation_token` makes the trigger `handle_new_user` create an `instructor` profile, link the invitation's instructor and set `accepted_at` in GoTrue's transaction, or abort the sign-up (`SB016` unknown token, `SB017` expired, `SB018` revoked, `SB019` used, `SB020` other address, `SB021` instructor inactive — defensive, deactivation already revoked the link, `SB022` instructor has an account). GoTrue hides that code behind a 500, so `/api/auth/signup` takes the reason from the invitation's state (`signupInvitation` in `src/lib/auth/invitation.ts`) and signs up with the invitation's address, never the form's.
- Rates (GLOSSARY „Stawka”, spec #93) are `public.rates`: one row per change, `rider_id` NULL = stable rate (always with an amount), otherwise an individual rate whose NULL amount means "back to the stable rate"; `from_month` is the first day of the month, `amount` integer grosze 0..1 000 000, one change per (stable, rider-or-none, month) (`rates_one_change_per_month_key`, NULLS NOT DISTINCT — upsert overwrites). Owner-only RLS (`private.owned_stable_id()`, individual rates only for `private.is_rider_of_my_stable`). Trigger `rates_month_rules`, also for `postgres`: a change only from the current or next month (`private.warsaw_month_start()`, `SB026`), only a planned change can be deleted (`SB027`; FK cascades pass), key columns immutable (`SB028`). Which rate applies in a month is decided by `src/lib/settlements/rates.ts` (first stable rate applies backwards); amounts are computed only in `src/lib/settlements/settlements.ts` and printed by `formatMoney`. Extra costs (GLOSSARY „Koszt dodatkowy”, #96) are `public.extra_costs`: stable, rider (FK cascade), `month` (first day), `name` 1–80 chars trimmed, `amount` integer grosze 1..10 000 000; owner-only RLS, writes only for `private.is_rider_of_my_stable`; trigger `extra_costs_month_rules` (also `postgres`) refuses a future month (`SB029`); only `name` and `amount` are updatable (column grant). „Do zapłaty” = rides amount + costs (`riderAmounts`); riders to pick for „Dopisz koszt” are the `rider` profiles the owner can read (`listStableRiders`).
- Riders cannot SELECT other riders' bookings (RLS). Slot occupancy comes from the RPC `public.get_slot_occupancy(stable_id, day)` — `security definer`, returns only `(instructor_id, hour, taken)`. Wrapper in `src/lib/bookings/queries.ts`.

## Conventions the config does not show

- Statistics are computed in one place: `computeStableStats` in `src/lib/stats/stats.ts` returns the page's view model; the page and components only render it.
- A ride (GLOSSARY „Jazda”) is defined once: `isRide` / `slotEndedAt` in `src/lib/bookings/rides.ts`, read by the statistics and the month summary. The month summary (GLOSSARY „Podsumowanie miesiąca”) is computed in `src/lib/month-summary/` (`summary.ts` core on the shared `SummaryBooking` shape, one file per role, e.g. `owner.ts`); its pages only load rows and render.
- The rider settlement PDF (spec #100) is content from `src/lib/settlements/document.ts` (availability `isSettlementPdfAvailable`, `composeSettlementDocument`, file name) drawn by `src/lib/settlements/pdf/render.ts` (jsPDF + jspdf-autotable). Only the endpoint `src/pages/osrodek/rozliczenia/[jezdziec]/pdf.ts` loads the renderer, by dynamic `import()` (Workers Free: 10 ms CPU per request); `astro.config.mjs` aliases jsPDF's browser dependencies (html2canvas, canvg, dompurify) to a stub. The font module `pdf/fonts.ts` is generated by `npm run pdf:font` — never edit it by hand. When the PDF is unavailable the endpoint redirects to the rider page; read/render failures are logged and come back as the banner `SETTLEMENT_PDF_FAILED`.
- Charts use `src/components/ui/BarChart.astro` (server-rendered, no client JavaScript); extend it rather than adding a chart dependency.
- Time and "today" are injected as defaulted parameters (`todayIso(now)`, `currentWarsawHour(now)`), so tests need no mocks or fake timers. Vitest files sit next to their module with Polish `it()` descriptions.
- The Claude Code hook `.claude/hooks/post-edit.mjs` runs Prettier on every Write/Edit and related Vitest tests in risk areas; its failure comes back as stderr. ESLint runs at commit (lint-staged) and in CI.
